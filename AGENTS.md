## Overview

Nested Properties is an Obsidian plugin that lets you view and edit nested frontmatter properties, rendering nested YAML objects and arrays as a collapsible tree inside the Properties editor (with context menus, add/cut/copy/paste/remove, and horizontal scrolling). It is built on `obsidian-dev-utils`.

## Architecture

- **Root config files** are thin re-exports — actual logic lives in `scripts/` (`eslint.config.mts` → `scripts/eslint-config.ts`, etc.).
- **`src/`** — plugin source:
  - `main.ts` — Obsidian entry point (default export of `Plugin`); imports the global stylesheet.
  - `plugin.ts` — `Plugin` extends `obsidian-dev-utils`' `PluginBase`; `onloadImpl()` wires the `PluginSettingsComponent` (persistence via `PluginDataHandler`), adds the `PluginSettingsTabComponent` wrapping the `PluginSettingsTab`, adds the `NestedPropertyRendererComponent` (passing it the settings component) and registers the `toggle-full-key-display` command (delegates to the renderer's `toggleFullKeyDisplay()`), adds the `NestedPropertyVaultOpsComponent` with the `rename-nested-property-across-vault` / `delete-nested-property-across-vault` commands, and adds the `NestedPropertySearchPatchComponent` (nested-property support in native search; no command).
  - `plugin-settings.ts` / `plugin-settings-component.ts` / `plugin-settings-tab.ts` — `PluginSettings` (data shape: `initialExpandLevel` — **defaulting to `0`, deliberately, so an upgrade changes nothing about how an existing vault renders; the collapsed row is made readable by its summary instead** — and `isFullKeyDisplayEnabled`), its `PluginSettingsComponentBase` subclass, and the declarative `PluginSettingsTabBase` tab. The tab exposes **only** `initialExpandLevel`: `isFullKeyDisplayEnabled` is deliberately absent from it, being controlled by the command and the Properties-header button, with the settings component only persisting that state. (Until `initialExpandLevel` there was intentionally no tab at all; the tab exists because that setting has no other control surface.)
  - `nested-properties-note-settings.ts` — the per-note override, read from a note's `nestedProperties` frontmatter key (camelCase, mirroring the `PluginSettings` field names one-to-one, as the author's other plugins do for their own keys). Read **synchronously** off `app.metadataCache.getCache(sourcePath)` rather than via `obsidian-dev-utils`' async `getFrontmatterSafe`, because the property widget's render path is synchronous. A value that is not a non-negative integer is not an override at all and falls through to the plugin setting.
  - `nested-property-vault-ops-component.ts` — `NestedPropertyVaultOpsComponent` (Obsidian `Component`), behind the `rename-nested-property-across-vault` / `delete-nested-property-across-vault` commands. All three operations (offer the paths with per-note counts, apply a rename, apply a delete) run over **one** private traversal, `iterateNotesWithNestedProperties()` — `vault.getMarkdownFiles()` → `metadataCache.getFileCache(file)?.frontmatter` → skip when absent → yield the note with its `collectNestedPropertyPaths()`. It is a **generator**, not a materialized list, so each note's cache read still happens immediately before that note is written rather than once up front for the whole vault. A full vault scan is the correct shape here: the metadata cache has no "notes carrying this property key" index, so there is no narrower set of notes to route the operation through. Writes go through `obsidian-dev-utils`' `processFrontmatter`, **not** the raw `fileManager.processFrontMatter` — that is what gives these vault-wide writes the shared `process()` primitive's resource locking, abort handling and timeout notices, so the component takes a `resourceLockComponent` alongside its `pluginNoticeComponent`.
  - `nested-property-renderer.ts` — `NestedPropertyRendererComponent` (Obsidian `Component`); the core renderer that wires up the property widgets, patches, context menus, expand/collapse state, and the floating scrollbar. `toggleFullKeyDisplay()` flips a `nested-properties-full-key-display` body class across all windows (via `AllWindowsEventComponent` + `getAllDomWindows`), which the stylesheet uses to show full (untruncated) keys — both **top-level** object property keys and **nested** keys — and persists the new state via the injected `PluginSettingsComponent` (read back on load to restore it). Because key text is rendered in `<input>` elements, full display works by widening (`width: auto`) rather than wrapping; each input's `size` is set to its value length (`renderComplexWidget` does this for the native top-level key input, `renderKeyEl`/`renderEntry` for nested ones) so `width: auto` can expand it — the `size` stays inert while the toggle is off because Obsidian's default input width wins. The same toggle is exposed as an inline `clickable-icon` button (`.nested-properties-full-key-toggle`) injected into the Properties header actions by `injectHeaderButtons`; its active appearance is driven purely by the body class (no per-button state sync). **Expand/collapse state is a `Map<string, boolean>` (`expansionOverrides`), not a set of expanded paths**: an absent path means the user has expressed no opinion and falls back to the initial expand level (`isExpanded()` — the note's own `nestedProperties.initialExpandLevel`, else the plugin setting, compared against `getPathDepth()`), so every write must be an EXPLICIT `true`/`false`, `collapseAllIn` included — deleting a path would re-expand whatever the user just collapsed. Depth is counted on the `sourcePath:`-stripped key (a source path legitimately contains dots), and an array index is a level of its own.
  - `value-utils.ts` — pure helpers for converting frontmatter values between property types, value-shape type guards (`convertValue`, `isComplexValue`, `isSimpleArray`, `isLossyConversion`, etc.), and `formatValueSummary`, the one-line rendition shown in place of a collapsed value (a complex value nested inside it is elided as `{ ... }` / `[ ... ]`, so the collapsed row stays one line tall).
  - `type-change-modal.ts` — `TypeChangeModal` (Obsidian `Modal`) confirming a potentially lossy property-type change before applying it.
  - `floating-scrollbar.ts` — `FloatingScrollbarComponent` (Obsidian `Component`) providing a floating horizontal scrollbar for deeply nested property containers. **The `wheel` and `mousemove` listeners are attached to the `.metadata-container` elements (`syncListenerTargets()` / `collectListenerTargets()`, reconciled by `update()`), never to a document.** It has to call `preventDefault()` to turn a vertical wheel into a horizontal scroll, so it cannot be passive, and Chromium makes every wheel event in the whole app wait on the main thread for a non-passive wheel listener registered on a document — which is what produced `[Violation] Handling of 'wheel' input event was delayed`. The Properties editor root is the right anchor because, unlike a property row, it does not come and go as rows collapse, start overflowing or are edited, so no listener can be stranded; targets are collected across **every** window, since reconciling against `activeDocument` alone would strip a background pop-out's listener. `mousemove` rides the same target set for the same reason: `handleNativeScrollbarCursor` walks a `:has()` selector on every move it is offered and forces layout (`scrollWidth`, `getBoundingClientRect()`) on any move landing inside an overflowing property, and on a document that is charged to every pointer move in the app. **Scoping it needs no `mouseleave` teardown, and adding one would be a behavior change rather than a fix**: the handler only ever toggles the class on the property under the pointer and returns at `closest()` otherwise, so the document listener never cleared a stale class on the way out either — every event that *can* clear the class is targeted inside that property and so reaches the container listener too. `should leave the class set when the pointer leaves the properties editor` pins that, and passes identically on both arrangements. `update()` **returns before its first layout read** when the document holds no matching property (the `.status-bar` `offsetHeight`, `scrollWidth` and `getBoundingClientRect()` reads force synchronous layout, and most notes have nothing to measure). Scroll-driven updates are coalesced into one animation frame (`scheduleUpdate()`), owned by the window the scroll happened in, and any queued frame is cancelled both on unload and at the top of `update()` so the pending-frame guard cannot stick if that frame never runs. `update()` itself stays **public and synchronous**, because `NestedPropertyRendererComponent` calls it directly after rendering and after an expand/collapse. Its **wheel-over-the-native-scrollbar** path — a wheel turn inside the 16px zone above an overflowing root property's bottom edge scrolls that property horizontally and consumes the event — is proved against a real Obsidian by `floating-scrollbar.desktop.integration.test.ts`, which hit-tests the point with `elementFromPoint` and dispatches at whatever is under it, so it covers registration-to-delivery rather than just the handler; the unit suite covers the handler. **Arranging the overflow is the non-obvious part**: nesting depth alone does NOT overflow, because every level is `width: 100%` in a column flex container and so shrinks by its own 20px indent (measured: `scrollWidth === clientWidth` at every level of an eleven-level note). Overflow needs a key too long to shrink **plus** full key display on, which gives key elements `width: auto; flex: 0 0 auto` — which is also the only way a user sees this scrollbar at all.
  - `patches/` — `MonkeyAroundComponent`-based runtime patches of Obsidian internals:
    - `metadata-type-manager-get-type-info-patch-component.ts` — patches `MetadataTypeManager.getTypeInfo` to route nested/complex values to the list, mixed-list, and object widgets.
    - `multi-text-property-widget-patch-component.ts` — patches the multitext property widget's `validate` to accept nested array values.
    - `unknown-widget-render-patch-component.ts` — patches the unknown-widget renderer to display nested objects/arrays.
    - `nested-property-search-patch-component.ts` — teaches Obsidian's **native global search** to match nested frontmatter (issue #1). Patches the internal property-matcher node's `match` to call the original first (top-level behavior untouched) then *add* matches for dotted nested paths (`[book.author: value]`), so nested queries work in the real search bar and compose with every other operator — no separate command. Bootstraps off the search view's first `startSearch` to reach the `SearchQuery` constructor, compiles a throwaway probe query to grab the shared property-matcher prototype, and structurally feature-detects that shape before patching (no-ops to native behavior if Obsidian's internals ever change). **Deviation:** Obsidian exposes no public API for search operators and `obsidian-typings` has no `SearchView`/`SearchQuery`/matcher types, so the component declares minimal best-effort internal interfaces reverse-engineered from the 1.13.3 build; these should be reported upstream to `obsidian-typings`. Verified end-to-end against real Obsidian by `nested-property-search-shared.integration.test.ts`, on both the latest public / min-supported **1.12.7** and catalyst **1.13.3** — the internal seam is version-sensitive, so both channels were run.
  - `styles/` — `main.scss` (plugin styles) and `scss.d.ts` (style-import type declaration).
- **`main` field** points to `src/main.ts` (Obsidian plugin source entry; built artifact is `dist/build/main.js`, not published to npm).
